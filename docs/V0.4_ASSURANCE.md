# Lumi Trace V0.4 Corpus and Training Assurance

## Scope

V0.4 establishes an auditable Python, finding-guided candidate-ranking corpus
and a fair local comparison between deterministic rankers and the smallest
credible learned reranker. It does not add vulnerability discovery, repair
generation, attack detection, hosted inference, or autonomous execution.

The evaluated product envelope remains:

```text
public vulnerability finding
-> inert exact-revision repository acquisition
-> label-blind bounded Python candidate generation
-> file and location-role ranking
-> aggregate evaluation
```

Repository intake never executes repository-controlled code. Qualification
uses one locked budget. The protected holdback has no runner command and
remains sealed and unopened.

## Governed storage

Identity-bearing data is outside the source checkout:

- `G:/Data/skylark-lumi-trace-eval/v0.4` holds governed source objects,
  rights evidence, audit cards, labels, partitions, features, private results,
  and any private checkpoint;
- `F:/Data/skylark-lumi-trace-eval/v0.4` holds bounded temporary workspaces and
  operational logs; and
- the source repository contains code, contracts, tests, documentation, and
  disclosure-safe aggregate evidence only.

No governed corpus, third-party repository snapshot, label, feature group,
checkpoint, or case-level result may be copied into a Python distribution or
the public evidence directory.

## Intake and item assurance

The builder implements proposal-before-fetch records, exact source and
revision identities, separate rights dimensions, append-only state
transitions, inert bare-Git acquisition, historical licence verification,
bounded tree and blob processing, path portability checks, submodule and LFS
controls, and zero checkout or repository execution.

Each admitted group is backed by:

- a source decision and rights matrix;
- vulnerable/fixed revision evidence;
- advisory and fixing-pair evidence;
- two controlled label passes produced without runner or model output;
- a resolution receipt;
- source, patch, advisory, target, and lineage fingerprints;
- poisoning, secret, privacy, prompt-text, and answer-leakage checks;
- natural hard negatives and a matched fixed control where available;
- an append-only state chain; and
- an identity-bearing group audit card.

The security policy quarantines every flagged path from derived model input.
An early whole-repository rejection rule was corrected without deleting its
history: reconsidered candidates receive new identities, successful
reconsiderations retire the old rejection through append-only correction
records, and all old evidence remains available privately.

## Independence and partitions

Repository organization lineages are assigned before feature design.
Assignments are never moved after acquisition. Aggregate supply extensions may
append only untouched, rights-approved organizations and may not inspect case
content, labels, features, rankings, or model output.

The final corpus seal rejects any family or fingerprint overlap across
training, engineering development, model selection, qualification, and
protected holdback. Within one partition, a shared source snapshot alone is
recorded as correlated evidence rather than incorrectly discarding distinct
vulnerability groups; only a matching composite group identity is
superseded.

The predeclared minimums are:

| Partition | Minimum groups | Minimum families | Additional control |
| --- | ---: | ---: | --- |
| Training | 500 | 25 | Rights, audit-card allowlist, max 25 groups per family |
| Engineering development | 100 | 8 | Threshold and candidate lock only |
| Model selection | 100 | 8 | Grouped selection only |
| Qualification | 97 | 8 | 97 matched safe controls; one run |
| Protected holdback | 97 | 8 | No opening in V0.4 |

The final pre-feature corpus seal contains:

| Partition | Accepted groups | Families | Matched controls |
| --- | ---: | ---: | ---: |
| Training | 541 | 317 | 541 |
| Engineering development | 158 | 12 | 158 |
| Model selection | 131 | 19 | 131 |
| Qualification | 202 | 10 | 202 |
| Protected holdback | 196 | 9 | 196 |

The 1,228 accepted groups are family-disjoint across partitions. The finalizer
recorded 486 fingerprint-overlap clusters, superseded only exact composite
group duplicates, found zero cross-partition family collisions, and left the
protected holdback unopened. It also terminalized 223 unselected fixing
proposals, explicitly quarantined 1,562 candidates outside the final
partition plan, and retained five incomplete reconsideration proposals as
quarantined rather than inferring a result.

## Candidate and metric lock

Candidate generation reads only finding text and the inert vulnerable snapshot.
Labels are applied after every ranking is sealed. Quarantined path identities
are excluded. Training preprocessing accepts only audit-card identities in the
final training manifest and final partition seal.

Engineering development freezes:

- a maximum of 2,000 candidates per group;
- V0.1.2 unchanged, lexical, sparse, random, and always-abstain comparators;
- file Recall@5, Recall@10, Recall@20, location-role Recall@20, MRR,
  hard-negative, family dispersion, and safety gates;
- the Python finding-guided product objective; and
- the learned-candidate material-gain, multi-family, cue-ablation, safety, and
  CPU selection rule.

Model selection cannot change those values. Qualification cannot begin without
the resulting candidate lock and qualification lock.

The first complete development run exposed symbol crowding under the
2,000-candidate cap. A file-only remediation then failed mathematically on
large trees, and a query-aware hybrid remained borderline. Those results and
partial caches were retained privately; none became the final lock.

The final label-blind candidate algorithm uses query-aware, corpus-frequency
weighted selection, a bounded file/symbol budget, and the sealed
`path-quarantine-except-labelled-target-v2` policy. The latter permits only an
already audited target path identity to override a snapshot quarantine false
positive; the ranker still receives no label, target bit, runner output, or
model output. The complete development run recorded 11 such overrides.

On all 158 development groups across 12 families, target indexability was
1.000. Sparse remained the strongest deterministic comparator and recorded:

- File Recall@5/10/20 of 0.494, 0.601, and 0.728;
- location-role-correct Recall@20 of 0.316;
- MRR of 0.405;
- hard-negative outrank of 0.222;
- family-macro Recall@20 of 0.762;
- minimum-family Recall@20 of 0.000; and
- one zero-recall family.

Sparse did not pass the locked V0.4 gates. V0.1.2 remained the unchanged
reference and completed 62 of 158 attempts; it was not selected. The separate
training preprocessing run covered all 541 allowlisted groups across 317
families with target indexability 1.000, while role Recall@20 remained 0.481.
The final Section 17 record therefore established candidate presence and a
genuine ordering and role-discrimination gap.

## Conditional TRACE-001 execution

V0.4 includes a bounded from-scratch pairwise linear reranker. The code has no
foundation model, tokenizer, model provider, remote-code path, or download
path. Its canonical JSON checkpoint has eight active numeric parameters and is
kept on governed private storage.

Training is fail-closed. Every Section 17 gate passed and the binding
recommendation changed to `TRACE_001_EXECUTION_AUTHORISED`. The first command
failed before optimisation because monolithic training-data identity
construction exceeded the hardened canonical JSON item bound. It wrote no
checkpoint. The failure was retained, identity construction was changed to
bounded per-group identities plus one aggregate identity, and the execution
lock and final gate record were superseded before resumption.

Two clean local runs then reproduced the same eight-parameter private
checkpoint over 541 groups and 1,522,092 pair updates. The experiment used no
foundation model, tokenizer, external weight, download, hosted service, or
remote code. Its int8 projection failed the locked regression gate at 0.93
top-one agreement.

On grouped model selection, TRACE-001 underperformed sparse:

| Metric | Sparse | TRACE-001 |
| --- | ---: | ---: |
| File Recall@20 | 0.809 | 0.718 |
| Location-role Recall@20 | 0.450 | 0.313 |
| MRR | 0.549 | 0.465 |
| Family-macro Recall@20 | 0.725 | 0.672 |

TRACE-001 improved two families and regressed five. It did not advance.

## Single-use qualification

The qualification lock is created from model-selection aggregates only. It
selects either the learned reranker or the strongest locked deterministic
candidate. Candidate generation, all frozen comparators, and the selected
candidate are then evaluated in one invocation.

The invocation:

- writes a consumption-start receipt before reading labels;
- denies Python socket creation;
- changes no threshold;
- emits aggregate metrics and Wilson intervals;
- spends the only qualification run; and
- leaves the protected holdback unopened.

An interrupted run is still spent. There is no retry command that silently
restores the budget.

The locked sparse candidate consumed the run on all 202 qualification groups
across 10 families with 202 matched safe controls. It passed target
indexability, Recall@10/20, MRR, family, completion, and safety floors but
failed:

- File Recall@5: 0.644 against 0.65;
- location-role Recall@20: 0.559 against 0.70;
- hard-negative outrank: 0.211 against a maximum 0.20; and
- wrong-location-role top one: 0.252 against a maximum 0.15.

The run is consumed, no retry remains, and the closure is
`NO_MODEL_ADVANTAGE / DETERMINISTIC_ROUTE`. The protected holdback remains
sealed and unopened. The controlled shadow-pilot package is prepared but not
ready for activation.

## Public evidence

`evidence/v0.4` is an aggregate projection. It contains no repository or case
identity, source, label, path, symbol, revision, diff, private checkpoint,
training feature, customer data, or protected-holdback substance. Its review
is a controlled internal release review, not a third-party audit.

Source publication, repository visibility changes, tags, releases, and weight
publication remain separate user decisions.
