# Lumi Trace V0.4 Controlled Shadow-Pilot Package

This package prepares, but does not start, a customer-owned shadow pilot.
The sealed V0.4 qualification did not pass, so pilot readiness is `NOT_READY`.
Any later activation requires new independent evidence, a passing
qualification, and separate customer and user approval. This package does not
authorise repository upload, production
blocking, automated remediation, disclosure, training-data use, or weight
publication.

## Supported use

The supported pilot use is finding-guided candidate ranking on an authorised
local Python repository. A customer supplies a structured security finding and
a local repository snapshot. Lumi Trace returns ranked files, symbols, and
locations for human review. It does not discover vulnerabilities, determine
exploitability, certify that a repository is safe, generate repairs, detect
attacks, or take autonomous action.

Pilot output is advisory. A qualified human reviewer remains responsible for
interpreting the finding, inspecting the proposed locations, and deciding any
engineering or security response.

## Installation and hardware check

Use a customer-controlled workstation with:

- Python 3.11 or newer;
- at least 16 GiB RAM;
- sufficient encrypted local disk for the authorised repository and output;
- no required GPU, hosted inference service, model provider, or API key; and
- Docker only when the customer separately opts into explicit reproduction.

Install from the reviewed source revision or its verified wheel. Before an
engagement, record the source or wheel hash, run the package verifier, run
`lumi-trace version`, and confirm that the reported runtime identity matches
the approved pilot manifest. If reproduction is authorised, run
`lumi-trace status` with an already-present digest-pinned Linux image. Lumi
Trace must not pull an image.

## Local data flow

```text
authorised finding + authorised local repository
  -> clean-room local snapshot and immutable identity
  -> deterministic local index
  -> bounded local candidate ranking
  -> optional customer-authored reproduction in network-denied Docker
  -> local JSON/SARIF evidence package
  -> human review
  -> optional local feedback record
```

No stage requires a network connection. Pilot setup should use an outbound
network-denied execution account or host policy where practical. The optional
reproduction lane is additionally isolated by the runtime's qualified Docker
sandbox.

## Authority and consent

Before every repository is processed, the customer must attest that:

- it controls the repository or is authorised to analyse it;
- the finding may be processed for the stated defensive purpose;
- applicable confidentiality, employment, and customer obligations permit the
  local analysis;
- any reproduction plan is authorised and contains no live-target action; and
- the named operators may view the resulting paths, symbols, and findings.

Evaluation permission and training permission are separate:

- the default pilot consent is `LOCAL_EVALUATION_ONLY`;
- no pilot material is admitted to training;
- feedback does not imply training consent; and
- any future training proposal requires explicit consent plus the complete
  item-level V0.4 rights, provenance, label, privacy, security, and independence
  audit.

## Privacy, retention, export, and deletion

Repository source, findings, paths, symbols, output, and feedback remain on
customer-controlled storage. Skylark receives only aggregate, customer-approved
pilot observations unless a separate transfer agreement identifies exact
material and purpose.

Before the pilot starts, agree:

- the local output root and its access controls;
- a retention deadline;
- whether aggregate metrics may be exported;
- the approved export recipient and transport;
- incident contacts; and
- deletion verification.

Export only the agreed package. The default export contains aggregate counts,
latency, supported/unsupported outcomes, and user-approved qualitative
feedback; it excludes source, finding text, repository identity, paths,
symbols, locations, diffs, raw output, secrets, credentials, and personal
data. At closure, delete the local working copy and derived output using the
customer's approved disposal process, then retain a deletion receipt containing
only the approved artifact identities, timestamps, and operator attestation.

## No-upload verification

Before processing customer material:

1. inspect installed dependencies and confirm that no hosted inference client
   or telemetry uploader is configured;
2. clear proxy variables and deny outbound network access for the process;
3. run a synthetic fixture through the same command and observe zero outbound
   connection attempts using the customer's network-control tooling;
4. verify that all input, temporary, cache, and output paths resolve to
   customer-controlled local storage; and
5. retain the command, package identity, network-policy identity, and result as
   the no-upload receipt.

A failed check blocks customer input. Do not work around the control by
disabling monitoring or moving data to an unapproved host.

## Unsupported input policy

Stop and return an unsupported or insufficient-evidence result when the input:

- is outside the authorised repository or finding scope;
- requires a remote repository, remote artifact, API key, hosted inference, or
  live-target access;
- is non-Python under the V0.4 claim;
- contains unsafe archives, links, special files, path-normalisation hazards,
  or unbounded material;
- needs repository-controlled setup, build, test, notebook, macro, hook, or
  package-manager execution;
- cannot be assigned an immutable repository identity;
- lacks enough evidence for the requested disposition; or
- requests vulnerability discovery, exploitation, repair generation, attack
  detection, autonomous blocking, or response.

Unsupported material is not silently coerced into the supported envelope.

## Human review and feedback

For each result, a reviewer records whether the proposed file and location were
useful, the correct location role, any misleading hard negative, and whether
the result affected a decision. Reviewers must not describe an abstention as a
safe-repository conclusion.

Corrections are append-only. Preserve the original output identity, the
reviewer's correction, reason, evidence, time, and superseding record identity.
Feedback remains evaluation-only unless a later governed intake explicitly
admits it. Aggregate reporting must not expose repository, finding, source,
path, symbol, or reviewer identities.

## Secret, privacy, and unexpected-data incident

If a secret, credential, personal datum, customer identifier, unapproved
repository, or unexpected executable artifact appears:

1. stop processing the affected item;
2. isolate the output without copying the sensitive match into tickets or
   public logs;
3. notify the customer's named incident contact;
4. record only a non-sensitive incident identity and category;
5. follow the customer's rotation, privacy, or disposal procedure; and
6. resume only after written scope and remediation approval.

The affected material is never used for training or public evidence.

## Pilot closure report

The closure report must record:

- approved runtime, evaluator, package, and pilot-manifest identities;
- authority and no-upload receipt identities;
- attempted, completed, unsupported, and insufficient-evidence counts;
- aggregate ranking and role-correctness metrics permitted by the customer;
- latency, peak memory, disk, and optional sandbox resource summaries;
- observed false-supported, safe-control, and unsafe non-abstention counts;
- incidents and corrections by non-sensitive category;
- human usefulness feedback;
- retention, export, and deletion receipts;
- whether the V0.4 supported-use statement remained accurate; and
- one decision: continue unchanged, narrow the envelope, remediate and repeat
  with a new independent partition, or stop.

The report must state that the activity was a controlled customer-owned shadow
pilot, not a third-party audit or production security control.
