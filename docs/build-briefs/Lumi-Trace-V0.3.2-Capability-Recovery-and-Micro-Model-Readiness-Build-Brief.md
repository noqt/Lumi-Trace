## 1. Purpose

V0.3.2 must convert the V0.3.1 diagnostic result into the strongest honest,
locally deployable Lumi Trace capability that the available evidence can
support.

This is not a one-defect patch brief. Codex is authorised and expected to
continue through the dependent problems exposed after the first defect is
fixed:

- runtime and schema validity;
- resource limits;
- repository materialisation and target indexability;
- candidate recall and location-role selection;
- hard-negative discrimination;
- safe disposition and abstention;
- corpus scale, diversity, rights, and label quality;
- micro-model necessity and feasibility;
- CPU, memory, disk, and optional GPU constraints;
- qualification integrity;
- reproducibility, security, packaging, and evidence sealing; and
- a bounded Trace IR attack-evidence feasibility lane.

The required objective is positive but not predetermined. Positive means one
of:

1. a qualified deterministic Trace Code capability;
2. a qualified narrowly scoped micro-model improvement over deterministic
   Trace;
3. a qualified narrower product envelope, such as Python-only vulnerability
   localisation, with unsupported cases rejected safely; or
4. a precise external blocker with all safe in-scope remediation exhausted
   and a ready-to-execute continuation package.

A threshold pass must never be manufactured by leakage, case-specific rules,
post-qualification tuning, unsafe scope expansion, or suppression of failed
attempts.

## 2. Starting evidence

V0.3.1 admitted 58 evaluation-only groups from 10 unrelated public repository
families:

- 29 vulnerable groups;
- 29 fixed safe controls;
- 40 development groups;
- 18 unopened qualification groups; and
- 52 natural hard negatives.

The unchanged Lumi Trace V0.1 runtime completed only 8 of 40 development
attempts:

- 28 attempts failed because score-reason generation retained up to 10
  identifier matches or 20 message matches while runtime verification allowed
  at most 8;
- 4 attempts reached a resource limit; and
- replay reproduced the failure semantically and by identity.

The observed recall, indexability, hard-negative, and disposition values are
diagnostic only. They are not a valid natural capability baseline because the
completion-integrity gate failed.

The 18 qualification groups remain unopened. Their one-run budget remains
unused. This is a protected programme asset.

## 4. Operating principles

### 4.1 Repair and continue

A remediable failure is a routing event, not automatic programme closure.
Codex must:

1. classify the failure;
2. preserve the failed condition and its identity;
3. state a falsifiable remediation hypothesis;
4. implement the smallest general correction;
5. add a regression test;
6. issue a new identity where required;
7. rerun affected development evidence;
8. compare against the prior condition; and
9. continue to the next blocker.

Codex should pause only for:

- an unavailable legal or data right;
- credentials or private access not already supplied;
- destructive action outside the governed workspace;
- public release or weight publication;
- protected-holdback access; or
- a material product decision that cannot be resolved from the objective and
  evidence.

### 4.2 Development evidence may guide development

The 40 development groups may be inspected, profiled, and rerun. Case-level
knowledge may inform general engineering fixes, but no exact path, repository,
revision, label, or vulnerability-specific exception may be encoded in the
runtime.

Every behavior change must be checked using repository-family-aware analysis
or leave-one-family-out tests where practical.

### 4.3 Qualification remains blind

Qualification identities, labels, case contents, and results remain
evaluator-only until:

- implementation and dependencies are locked;
- the development run completes;
- thresholds are fixed;
- model and comparator selection is complete;
- all safety and integrity floors pass;
- the qualification run manifest is sealed; and
- the one-run decision is recorded.

If qualification fails, that partition is spent. It may be reported but not
used for tuning. A future attempt requires a newly sourced,
repository-disjoint qualification partition.

### 4.4 Deterministic systems retain authority

Any learned component may rank, classify, or score bounded candidates. It may
not control provenance, repository acquisition, policy, sandboxing, evidence
identity, qualification, final disposition, or release.

### 4.5 Narrowing is preferable to unsafe generalisation

V0.3.2 may qualify a constrained capability if the broader capability is not
yet supported. Scope must be explicit and enforced in code. Unsupported
languages, repository shapes, finding types, or evidence conditions must fail
closed.

## 5. Identity and change-control policy

The V0.1.0 wheel and V0.3.1 evidence remain immutable.

Use the following identity progression:

- `0.1.1`: contract-validity and bounded resource correction that preserves
  intended ranking behavior;
- `0.1.2` or later: deterministic index, ranking, role, or disposition changes;
- Trace-Eval `0.3.2` or later: evaluator or metric implementation changes; and
- `TRACE-001` experiment identities: learned components, training
  configurations, datasets, and weights.

Do not combine results from different identities into one baseline. Every
comparison must state:

- runtime version and wheel hash;
- evaluator version and wheel hash;
- schema and algorithm identities;
- corpus and split identities;
- dependency lock identity;
- configuration and limit identity;
- hardware class;
- cold or warm cache state; and
- evidence seal identity.

If a contract change is backward incompatible, create a new schema version.
Do not silently reinterpret an existing artifact.

## 6. Workstream A - Runtime contract recovery

### 6.1 Canonical score-reason bound

The preferred remediation is to establish one canonical score-reason match
bound shared by:

- the producer;
- runtime verification;
- the JSON schema;
- documentation; and
- tests.

Because the current producer intentionally scores up to 20 message matches and
the schema declares no eight-item maximum, first evaluate a canonical maximum
of 20. Preserve ranking points, ordering, and evidence content where possible.

If compatibility analysis shows that formalising 20 under
`candidate-set-v1` changes an externally relied-upon contract, introduce a new
schema version instead of silently changing V1.

Required regression coverage:

- 0, 1, 8, 9, 10, 20, and 21 matches;
- identifier and message reason types;
- duplicate, empty, non-string, and unsorted matches;
- schema/runtime agreement;
- generated artifacts always pass their own verifier;
- stable canonical identity; and
- unchanged ranking scores and order for the V0.3.1 development inputs.

### 6.2 Contract round-trip invariants

Add tests or generated checks proving that every public producer emits an
artifact accepted by:

- its runtime verifier;
- the packaged JSON schema;
- the CLI validation path; and
- evidence package verification.

Cover repository indexes, candidate sets, findings, plans, receipts, bundles,
and evidence manifests. Producer/verifier disagreement is a release blocker.

### 6.3 V0.1.1 release condition

Build two clean V0.1.1 wheels and require byte identity or a documented,
bounded platform variance. Install the built wheel into a clean evaluator
environment. Evaluation must not import unbuilt local source.

## 7. Workstream B - Resource-limit recovery

The four V0.3.1 resource failures must be diagnosed separately from the
contract defect.

Instrument development runs with bounded, disclosure-safe observations for:

- stage wall time;
- process and child-process CPU time;
- peak resident memory;
- file and directory counts;
- total and indexed bytes;
- oversized, binary, encoding, generated, and vendored exclusions;
- token and symbol counts;
- archive or checkout materialisation time;
- index construction time;
- ranking and verification time;
- disk read/write volume where available;
- cache state; and
- termination reason.

First rerun the affected development cases under the original limits with
instrumentation. Classify each failure as:

- runaway or algorithmic defect;
- repository-size or file-count pressure;
- memory pressure;
- disk or cold-cache pressure;
- subprocess deadlock;
- evaluator overhead;
- environmental contention;
- a legitimate unsupported envelope; or
- an insufficient time budget for otherwise bounded work.

Change a limit only after classification. Any increase must retain a hard
ceiling, include a worst-case test, and be reflected in the declared supported
hardware envelope.

The target is:

- 40 of 40 development attempts terminate with a valid typed result;
- zero unexplained timeouts or kills;
- zero unbounded work;
- no dependence on a warm cache for correctness; and
- a resource profile suitable for repeatable local use.

Unsupported oversized inputs may fail closed, but they count against broad
coverage claims and must be represented in scope documentation.

## 8. Workstream C - Valid development baseline

After workstreams A and B:

1. seal the V0.1.1 runtime, evaluator, limits, corpus, and 40-group development
   run manifest;
2. execute all development groups from disposable cold workspaces;
3. retain raw governed outputs before scoring;
4. verify every attempt and artifact;
5. replay the full run or a predeclared representative subset;
6. calculate micro, repository-family macro, and stratum metrics; and
7. issue a separate V0.3.2 baseline evidence record.

No capability metric is valid unless all 40 attempts produce valid typed
results and all integrity floors pass.

The inherited provisional performance gates are:

| Metric | Gate |
| --- | ---: |
| Target indexability | at least 0.90 |
| File recall at 20 | at least 0.70 |
| Hard-negative outrank rate | at most 0.25 |
| Wrong-location-role top-one rate | at most 0.25 |
| False supported disposition | exactly 0 |
| False vulnerability rate | exactly 0 |
| Unsafe non-abstention | exactly 0 |

Record confidence intervals and per-family dispersion. A micro-average pass
with catastrophic family failures is not sufficient for a broad claim.

## 9. Workstream D - Indexability recovery

If target indexability is below 0.90, do not train a model. Audit every missing
development target and assign one or more general causes:

- repository materialisation or revision mismatch;
- path normalisation, rename, case, symlink, or submodule handling;
- unsupported encoding or binary classification;
- language detection;
- generated, vendored, ignored, oversized, or extension exclusion;
- file, byte, line, token, or traversal budget;
- parser or symbol-extraction failure;
- label target absent from the sealed revision;
- source location represented only through an alias, wrapper, macro, template,
  generated artifact, or configuration;
- finding-to-repository identity mismatch; or
- evaluator matching defect.

For each cause:

- preserve affected governed evidence;
- establish whether the label or runtime is wrong;
- add an owned or permissively licensed minimal fixture;
- implement a general correction;
- verify resource boundedness;
- rerun the affected cases and the full development set; and
- report new exclusions or scope constraints.

Prioritise file-level visibility before symbol and region sophistication.
After file indexability passes, improve symbol and region representation where
it materially supports role-correct ranking.

Do not add task-specific target paths, repository names, revision hashes, or
vulnerability identifiers to product behavior.

## 10. Workstream E - Ranking, role, and safe disposition

Enter this workstream only when candidate targets are usually indexable.

### 10.1 Failure decomposition

Measure separately:

- target absent from index;
- target absent from top 20;
- target present but below a lexical decoy;
- target present but below a harness, test, witness, crash site, or fix-only
  location;
- correct file but wrong symbol or region;
- vulnerable revision confused with fixed safe control;
- explicit path or symbol cue overtrust;
- score instability or tie behavior;
- unsupported input accepted;
- insufficient evidence promoted; and
- safe case not abstained.

### 10.2 Deterministic remediation

Codex may improve:

- finding normalisation;
- path and symbol cue calibration;
- implementation-versus-observation features;
- test and harness treatment;
- vulnerable/fixed evidence-pair relationships;
- hard-negative features;
- location-role representation;
- candidate diversity;
- deterministic score weights;
- confidence calibration; and
- abstention rules.

Every change requires:

- a stated development hypothesis;
- a new runtime or algorithm identity;
- a general regression fixture;
- same-package comparison;
- repository-family-aware evaluation;
- safety-floor verification; and
- a change log that records failed as well as successful experiments.

Do not optimise a single aggregate metric while degrading safe controls,
minority families, or no-cue strata.

### 10.3 Cue ablation

Report natural, no-path, no-symbol, reduced-description, and other predeclared
cue ablations separately. Ablations do not create additional corpus groups.

The product must not claim vulnerability reasoning if performance depends
principally on answer-like paths or symbols supplied in the finding.

## 11. Workstream F - Corpus and label sufficiency

The current 58 groups are a valid evaluation pilot but not a training corpus.
If the corrected baseline supports continued development, scale through the
existing governed intake path.

Training-readiness targets remain:

- at least 500 useful labelled candidate-ranking groups;
- at least 25 unrelated repository families with appropriate training rights;
- repository-family-disjoint training, development, qualification, and
  protected holdback partitions;
- meaningful vulnerable/fixed controls and hard negatives;
- audited location-role labels;
- reproduction witnesses for any reproduction claim;
- enough no-cue and weak-cue cases to measure leakage; and
- language diversity matching the intended product claim.

### 11.1 Rights

Track evaluation, retention, redistribution, publication, and training rights
separately. No right may be inferred from another.

The 58 V0.3.1 groups remain evaluation-only unless re-reviewed. Any group moved
to training eligibility must leave all qualification and holdback partitions,
receive a new lineage record, and retain its earlier evaluation exposure
history.

### 11.2 Diversity

The current pilot is Python-only. Codex may:

- qualify a Python-first product if the evidence supports it; and
- add other languages incrementally through separate strata before making a
  multi-language claim.

Prioritise languages and repository forms based on target users, incident
evidence, existing deterministic parser support, and achievable label quality.
Do not dilute the corpus with low-quality groups merely to reach counts.

### 11.3 Perceived independence through controls

External review is not mandatory for this build. Label and result credibility
must instead use controlled independence:

- label construction before Trace output is viewed;
- reviewer blindness to candidate rank and score;
- separate label and run identities;
- two-pass review for ambiguous or high-impact cases;
- deterministic conflict and leakage checks;
- sampled second review;
- signed review receipts;
- recorded rejection reasons; and
- aggregate disagreement reporting.

Codex may conduct both passes if the workflow prevents the second pass from
seeing the first conclusion until its own assessment is recorded.

## 12. Workstream G - Micro-model decision and experiment

### 12.1 Entry gate

A learned experiment is authorised only when all of the following are true:

- target indexability is at least 0.90;
- the accepted target is normally available within the bounded candidate set;
- remaining error is principally ordering, location-role selection,
  vulnerable/safe discrimination, evidence-pair scoring, or safe abstention;
- deterministic remediations have been tested and documented;
- at least 500 useful training-eligible groups and 25 unrelated
  training-eligible repository families are available;
- training, development, qualification, and holdback lineages are disjoint;
- label audits and hard negatives are adequate;
- foundation-model and dependency rights are verified;
- the training objective and metrics are locked; and
- no qualification or protected-holdback evidence is used for model selection.

If these gates are not met, Codex must continue the relevant deterministic,
data, or rights workstream rather than train prematurely.

### 12.2 Initial model role

The first model must have one narrow role selected from evidence:

- candidate reranker;
- vulnerable/safe discriminator;
- location-role classifier;
- evidence-pair scorer; or
- safe-abstention classifier.

It must not be an exploit agent, unrestricted security chatbot, repair
generator, command planner, actor-attribution model, or autonomous responder.

### 12.3 Model envelope

The experiment envelope is:

- no more than 1 billion active parameters;
- preferred comparison bands near 100M, 300M, and 1B;
- preferred quantised artifact no larger than 2 GiB;
- CPU-capable local inference on a 16 GB RAM workstation;
- optional consumer-GPU acceleration;
- no hosted inference dependency;
- no external tool authority; and
- structured, bounded output.

Codex should begin with the smallest credible statistical or encoder baseline.
Scale model size only when the additional capability is measured.

### 12.4 Comparator ladder

Compare:

- unchanged deterministic Trace;
- remediated deterministic Trace;
- random, majority, and always-abstain controls;
- a simple lexical or statistical model;
- a small encoder or classifier;
- an intermediate micro model;
- a sub-1B structured-output candidate if justified; and
- an appropriately licensed larger model as a ceiling comparator only when
  useful.

Select on locked development metrics with repository-family-aware analysis.
Record accuracy, safety, latency, memory, artifact size, energy or runtime
proxy, and failure behavior.

### 12.5 Supply-chain controls

Before any model or tokenizer download:

- verify the authoritative source and exact revision;
- review the licence and intended-use compatibility;
- record hashes and file inventory;
- prefer non-executable tensor formats;
- reject remote code requirements unless separately reviewed and sandboxed;
- scan dependencies and artifacts;
- block network access during ordinary inference;
- record model, tokenizer, framework, and quantisation lineage; and
- test malformed and adversarial input handling.

Training outputs remain private until a separate release decision.

## 13. Workstream H - Trace IR attack-evidence lane

Trace Code and Trace IR remain separate evidence domains. Code success does
not establish attack-detection capability.

After the core runtime and evaluation infrastructure are reliable, Codex may
build a bounded Trace IR feasibility extension using:

- Skylark-authored synthetic events;
- rights-cleared public defensive telemetry;
- isolated lab attack emulation;
- matched benign controls;
- inert event parsing; and
- no live response authority.

The first objective is event relevance and evidence sufficiency, not attack
attribution or autonomous response.

Required IR measurements include:

- malicious/benign discrimination;
- incident-family-disjoint evaluation;
- false-alert rate;
- unsafe non-abstention;
- event and evidence-pair recall;
- dependency on explicit indicators;
- replay determinism;
- latency and throughput; and
- robustness to malformed, duplicated, reordered, and injected event fields.

No natural attack-detection claim may be made from synthetic fixtures alone.
The IR lane must have separate corpora, labels, splits, identities, metrics,
seals, and closure.

## 14. Hardware and scheduling

### 14.1 CPU lane

Runtime repair, repository intake, materialisation, indexing, deterministic
ranking, most evaluation, evidence sealing, and small-model inference are
CPU-first.

Codex must:

- detect available CPU, memory, disk, Docker, and GPU resources;
- avoid fixed assumptions about worker count;
- default to one or two concurrent heavy repository jobs;
- expose bounded concurrency;
- separate cold and warm measurements;
- schedule full batches away from competing Lumi CPU-heavy builds where
  practical; and
- preserve correctness under reduced resources.

### 14.2 GPU lane

GPU use is optional until the learned experiment. Codex may use an available
GPU for:

- micro-model training;
- embedding or encoder experiments;
- quantisation validation; and
- throughput comparison.

GPU absence must not prevent deterministic work or CPU inference validation.
Every selected model must retain the declared CPU-capable local path.

### 14.3 Storage

All build, corpus, training, and evidence work must remain on approved F:/G:
storage. Do not move the project or governed artifacts to C:.

Separate:

- source repository;
- governed intake;
- immutable repository snapshots;
- labels and review records;
- development runs;
- qualification runs;
- training datasets;
- checkpoints and model caches;
- disclosure-safe public evidence; and
- disposable caches.

Validate target paths before recursive deletion or movement. Delete only
recoverable caches after evidence is sealed and verified.

## 15. Qualification policy

### 15.1 Deterministic qualification

Run the unopened 18-group V0.3.1 qualification partition exactly once only if:

- all 40 development attempts complete validly;
- integrity and safety floors pass;
- the selected deterministic runtime meets every locked gate;
- implementation, schemas, dependencies, limits, and thresholds are sealed;
- no further deterministic or model selection is planned from this partition;
- the runner is label-blind; and
- the qualification budget record is still 0 of 1.

### 15.2 Learned qualification

Do not use the same 18 groups to compare multiple learned candidates. Learned
model selection requires separate development data and a qualification design
locked before any learned qualification run.

If the original 18-group partition is consumed by deterministic qualification,
a future learned model requires a new repository-disjoint qualification set.

### 15.3 Qualification failure

On failure:

- seal and report the result;
- do not inspect labels for tuning;
- mark the partition spent;
- return to development using only authorised development evidence; and
- create a new independent qualification partition before another claim.

## 16. Integrity and safety floors

The following remain exactly zero:

- protected-holdback exposure;
- unauthorised corpus or repository access;
- cross-split repository-lineage overlap;
- label leakage into runner or model input;
- retained-evidence verification failure;
- producer/verifier contract disagreement;
- malformed-input false `SUPPORTED`;
- audited negative-control false `CONFIRMED`;
- unsafe non-abstention;
- false supported disposition;
- false vulnerability on mandatory safe controls;
- third-party source or case substance in public evidence;
- unreviewed executable model artifact loading; and
- network use during sealed local inference.

Same-host identity-bearing outputs must agree exactly on replay. Semantic
agreement is required where the contract intentionally excludes runtime
observations.

## 18. Problem-response matrix

| Observed problem | Required response |
| --- | --- |
| Producer output fails its verifier | Reconcile the contract, centralise bounds, add round-trip tests, issue a new runtime identity |
| Development attempt times out | Profile by stage, classify cause, bound the work, then adjust algorithm or limit |
| Target is absent from snapshot | Verify revision and label; fix materialisation or reject the label |
| Target file is excluded | Correct the general exclusion or explicitly narrow supported scope |
| Target is indexed but not top 20 | Improve deterministic retrieval before training |
| Target is top 20 but poorly ordered | Compare deterministic and learned reranking |
| Harness or witness outranks implementation | Improve location-role representation and hard-negative training |
| Fixed revision is marked vulnerable | Treat as a safety-floor failure; improve pair semantics and abstention |
| Performance collapses without path cues | Report cue dependence and improve semantic evidence representation |
| One repository family dominates | Use macro metrics, reweight data, and expand independent families |
| Python works but another language fails | Qualify Python separately; add language support before broader claims |
| Data count is too low | Continue rights-cleared intake; do not weaken labels |
| Training rights are absent | Keep material evaluation-only and source new training-eligible data |
| A comparator requires remote code | Reject it or isolate and separately review it |
| GPU is unavailable | Continue CPU work and select a CPU-capable experiment |
| Learned model does not beat simple baselines | Do not ship the model; retain deterministic product or narrow the task |
| Qualification fails | Seal it, spend the partition, do not tune on it, source a new partition |
| Trace IR synthetic results are strong | Seek natural rights-cleared telemetry before an attack-detection claim |
| Public evidence risks source disclosure | Block publication and reduce to verified aggregates |

language, rights, or sample coverage is not yet sufficient for qualification

external right, credential, dataset, hardware change, or public decision. The
closure must identify the exact blocker and include the ready continuation
